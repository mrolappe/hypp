**State: green.**

## Completed

- `internal/ByteReader.kt` — sequential big-endian `u8`/`u16`/`u32` reads,
  plus `decodeName()` (Latin-1 byte-for-char mapping, truncated at the first
  NUL; real charset decoding is phase 4).
- `Header.kt` — the 12-byte `HDOC` header.
- `IndexEntry.kt` — one real index-table entry (type-255 sentinel excluded),
  with `compressedLength` (derived, no length field in the format) and
  `uncompressedLength` (honouring the image `next`-overload: for type-3
  entries `next` holds the high bits of the uncompressed size, not a
  navigation link).
- `ExtendedHeader.kt` — `id` + raw `data`, generic for now (no known/unknown
  distinction yet — that starts once phase 4 gives specific ids, like
  charset, their own sealed variant).
- `OpenOutcome.kt` — `Success`/`Failure(OpenFailure)`; `OpenFailure` has one
  case so far, `InvalidMagic`.
- `HypDocument.kt` — `open()`: header, index table (even-padding via the
  stored `len` byte, no independent recomputation), extended headers with
  the corrected 4-byte terminator (see below), derived `compressedLength`
  using the next entry's `seek` or the file's own length as the final
  boundary.
- Vendored `empty.hyp`, `textattr.hyp`, `hcp_orig_en.hyp` under
  `src/commonTest/resources/corpus/` for provenance; embedded as base64 in
  `src/commonTest/kotlin/de/rholambdapi/hypp/TestCorpus.kt` for actual test
  use (see Decisions).
- Removed phase-1's `Placeholder.kt`/`SkeletonTest.kt`, superseded by real
  container code and tests that already prove all three targets work.

## Decisions

- **Multiplatform test-resource loading deferred; corpus embedded as
  base64 instead.** `src/commonTest/resources/` isn't reliably wired onto
  `wasmJs`/`wasmWasi` test execution without extra Gradle plumbing
  (untried, real toolchain work). Since the plan's own micro-corpus is
  deliberately small, the pragmatic zero-dependency fix is: vendor the raw
  `.hyp` files for provenance/hex-inspection, but embed their bytes as
  chunked base64 string literals (`kotlin.io.encoding.Base64`, stdlib) in
  `TestCorpus.kt`, generated by a one-off script. Chunked into ≤20000-char
  literals to stay well under the JVM class file's 64 KB per-string-constant
  limit — `hcp_orig_en.hyp` alone needs two chunks. Revisit if a later
  phase needs a corpus file too large for this to stay comfortable (the
  full 704-file wild sweep in phase 11 will need real HTTP fetching
  regardless, not resource loading).
- `IndexEntry.len` (the raw index-entry byte length) is kept on the public
  type even though it's mostly a parsing artifact — it's a genuine spec
  field and the plan's own red-test list asserts it directly.
- `ExtendedHeader` stays a single generic `Unknown` case for now; no
  `UnknownExtendedHeader` diagnostic is raised because nothing yet
  distinguishes a "known" id from an "unknown" one — that distinction
  starts existing once phase 4 adds a `Charset` variant.

## Bug caught by the integration test

`realDocumentEveryEntryInBounds` failed first with
`IndexOutOfBoundsException` — `hcp_orig_en.hyp` has **no trailing type-255
EOF sentinel at all** (`itableCount=124`, all real entries; the last two are
type-2 external references with `seek` already equal to the file length).
The two hand-verified tiny corpus files both happen to have one, which is
what "itableCount includes a trailing EOF sentinel" (stated in the plan)
generalized from. Fixed by deriving each entry's length against "next
entry's seek, or the file's own byte length if there is no next entry" —
see `doc/format-notes.md` for the full writeup. This is exactly the kind of
thing the plan's "real consumer as early as feasible" rule is for: the two
unit tests alone would never have caught it.
