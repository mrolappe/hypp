# hypp — Phases 12–19: `.REF` support, `hypp-cli`, renderers, traversal API

Approved 2026-08-18. A duplicate lives at
`~/.claude/plans/structured-twirling-puddle.md`, but this repo copy is
authoritative going forward, same convention as `doc/PLAN.md`.

**Execution mode (explicit user decision):** implementation is carried out
by delegating each step to sub-agents with model overrides (Opus/Sonnet/Haiku
per the per-step assignments below), each given the context needed for that
step. Not self-implemented directly. Nothing has been implemented yet as of
this writing — the plan below is approved but no phase has started.

## Context

hypp's original 11-phase plan (`doc/PLAN.md`) is complete: a clean-room Kotlin
Multiplatform `.HYP` parser with a full object model, published locally via
`includeBuild`, exercised against the full 702-file public corpus with zero
crashes. Two items were deliberately deferred at the time: `.REF` support and
write/round-trip. A CLI was brainstormed afterward (`doc/cli-design-space.md`)
but never decided or built — hypp today has no consumer outside its own test
suite.

This round picks up four of those loose ends together, since they compose:
`.REF` support (resolving cross-document link names), a real CLI
(`hypp-cli`, a separate published-consumer module, proving the library end to
end for a human), a pluggable renderer abstraction behind it (six formats:
HTML, Markdown, AsciiDoc, Org-mode, terminal/ANSI, EPUB), and a small
traversal-API gap closed in the core model so non-rendering consumers
(analysis/visualization) can resolve a link target without knowing which of
three nullable accessors to call.

Write/round-trip remains out of scope, unchanged from `doc/PLAN.md`.

Before planning, the `.REF` binary format was decoded from
`https://tho-otto.m68k.eu/hyp/reflink_orig_en.hyp` (the HCP author's own
documentation, itself a `.hyp` file, rendered via hypp's own `hyp2text`) and
cross-checked against `hyp.h`'s `HYP_MAGIC_REF = 0x48524546L` ('HREF'). The
open question of what a real file's `TYPE_EXTERNAL_REF` index entry actually
contains was also resolved empirically (below), against the vendored
`hcp_orig_en.hyp` fixture, rather than guessed.

## `.REF` binary format (authoritative, decoded — do not re-derive)

```
File I.D.: 4 bytes magic 'HREF'

Repeating, any number of times:
  Module-header:
    4 bytes: length of the module, NOT including this header
    4 bytes: number of entries in this module
  Module-data (that many entries):
    1 byte:  entry id
               0 = File name    (e.g. 'ST-GUIDE' — no path/ext normally; '.HYP' appended if none given)
               1 = Node name    (page name from the hypertext, belongs to the preceding file-entry)
               2 = Alias name   (optional, HCP-only)
               3 = Label name   (optional, HCP-only; string followed by 2 EXTRA bytes: a line number)
               4 = database name (belongs to the preceding file-entry)
    1 byte:  length of the entry string
    n bytes: entry as a NUL-terminated string
             (id 3 only: NUL-terminated string, then the 2-byte line number)

Terminator: 8 bytes of zero, in place of the next module-header, marks end of file.
```

Semantically: a `.REF` file is a library of modules (one per compiled `.hyp`
file) cataloguing that file's node/alias/label names, so other `.hyp` files'
external-reference entries (`IndexEntry.TYPE_EXTERNAL_REF`) can be resolved
across files at read time. No real `.REF` sample files exist in the public
corpus (checked the listing page — zero `.ref` links) — `.REF` tests are
necessarily synthetic.

## Resolved: what `TYPE_EXTERNAL_REF.name` actually contains

Inspected all 18 type-2 entries in `src/commonTest/resources/corpus/hcp_orig_en.hyp`.
**Finding:** one NUL-terminated string, `"<filename>/<nodename>"`, e.g.
`"ST-GUIDE.HYP/See also"`, `"reflink.hyp/REF-format"`. Casing/`.HYP` presence
is inconsistent — a different convention than the `.REF` file-name field,
not the same field reused. Two anomalies with no `/` (`"Options"`,
`"command extern"`) are recorded as unresolved, same treatment as other
`doc/format-notes.md` gaps — not guessed away.

## Design decisions (flagged explicitly)

1. `IndexEntry.externalRef()` splits `name` on the first `/`; no-`/` case yields `fileName = null`.
2. **New model addition**: `HypDocument.resolve(target: NodeIndex): ResolvedTarget` (sealed: `ToNode`/`ToImage`/`ToExternalRef`/`ToSystemAction`/`Missing`) — closes a real gap (link-target resolution today needs `entry.type` plus picking one of three nullable accessors), not speculative. Lives in `commonMain` (core-model concern).
3. **`hypp-cli` is a separate Gradle build** (`hypp-cli/settings.gradle.kts` + `build.gradle.kts`), consuming published `hypp` via `includeBuild("..")` plus the exact `dependencySubstitution` fix already recorded in `doc/LEARNINGS.md` § "Post-plan follow-up: includeBuild integration check" — not a same-repo subproject.
4. **`hypp-cli` is itself Kotlin Multiplatform from the start** (`commonMain`/`jvmMain`/`wasmWasiMain`/`macosArm64Main`), even though Round A only ships `jvm`. This is what lets renderers land once (Phase 15, `commonMain`) and be reused unmodified by Rounds C/D — only file I/O is `expect`/`actual`.
5. **Renderer abstraction is two small interfaces**: `Renderer` (`fun render(document): String`) for the five text-shaped formats, `ArchiveRenderer` (`fun render(document): List<RenderedFile>`) for EPUB alone (genuinely different output shape — a file set, not a string). No visitor/streaming machinery — documents are small; building one `String` in memory is exactly what `hyp2text`/`hyp2html` already do.
6. **EPUB's ZIP packaging is JVM-only** (`java.util.zip`) for now — a cross-platform ZIP+CRC32 writer for `wasmWasiMain`/`macosArm64Main` is real, unevidenced work. Rounds C/D simply don't offer `--format epub`.
7. **Markdown/AsciiDoc/Org share one `renderMarkup(document, syntax: MarkupSyntax)` walker**, parameterised only by token strings — three near-identical span-walkers is the textbook shared-code case.
8. **HTML's span/escaping logic extracted to shared `HtmlSpans.kt`**, reused by `HtmlRenderer` and `EpubRenderer` (EPUB bodies are XHTML). `hyp2html`/`hyp2text` in `hypp`'s own `commonTest` are left untouched (they stay the core library's integration-test consumers — Gradle doesn't share test source sets across modules anyway).
9. **ANSI renderer, two layers**: `AnsiStyle.sgrFor(style: TextStyle): String` (pure, stateless SGR mapping) + `styledLines(node: Node): List<StyledLine>` (a per-node structured intermediate, reusable by a future TUI) + a thin `AnsiRenderer : Renderer` built on both — the whole-document flatten is only the thin last layer.
10. **Image encoding is behind a small `ImageEncoder` interface** (`fun encode(image: ImageNode): ByteArray`), so the format is swappable per platform without touching `HtmlRenderer`/`extract-images`. Default (`commonMain`, used by every target): `StoredPngEncoder` — a real, spec-valid PNG written with deflate's RFC-1951 "stored" (uncompressed) block mode, needing only a hand-rolled CRC32 + Adler32 (~50 lines, no dependency, no LZ77/Huffman) — universally viewable, alpha-capable, same code on jvm/wasmWasi/macosArm64. `hypp-cli`'s JVM `Main.kt` (composition root) may construct with a better encoder instead — `ImageIoPngEncoder` (JVM-only, `javax.imageio`, real deflate compression) — without any change to `HtmlRenderer`/`Commands.kt`, which only depend on the `ImageEncoder` interface. GIF/LZW considered and rejected as the *default* (more hand-rolled code than stored-block PNG for a smaller-but-not-required win); nothing stops it being added later as another `ImageEncoder` implementation behind the same interface.
11. **Fat jar via a hand-rolled `Jar` task** (zipTree over `runtimeClasspath`), no Shadow plugin — `hypp-cli`'s only deps are `kotlin-stdlib` and dependency-free `hypp-jvm`, so there's nothing to shade.
12. **GraalVM (Round B) via a hand-rolled opt-in `Exec` task** invoking `native-image` directly, mirroring `corpusSweep`'s "opt-in, not part of build/check" pattern — no new Gradle plugin.
13. **Round D's native target is `macosArm64`** (the actual dev machine). `linuxX64`/`mingwX64` and any CI matrix are an explicit follow-up, out of scope here.
14. **`dump`'s default `--format` is `html`** — the most complete renderer today.
15. **`validate --strict` hard/informational diagnostic split is CLI-local policy**, not pushed into `commonMain`'s neutral model.
16. **No new test dependency for property-based `.REF` tests** — hand-rolled `kotlin.random.Random` generator with fixed seeds, consistent with the rest of the project.

Typst/AmigaGuide renderers are explicitly **not** built now — the abstraction above is what makes them "a single new small file" later.

## Phase 12 — `.REF` parsing

**Model/effort:** Opus (spec-to-model design, medium) for the `RefFile` parser and grouping semantics; Sonnet (low) for `IndexEntry.externalRef()`; Haiku (low) for the property-generator's byte-encoding boilerplate and the doc write-up.

**Files:** `src/commonMain/kotlin/de/rholambdapi/hypp/RefFile.kt` (new), `IndexEntry.kt` (add `ExternalRef` + `externalRef()`), `src/commonTest/kotlin/de/rholambdapi/hypp/RefFileTest.kt`, `RefFilePropertyTest.kt`, `doc/format-notes.md` (record the finding above with evidence), `doc/progress/phase-12-ref-support.md`.

1. `IndexEntry.externalRef(): ExternalRef` (`data class ExternalRef(val fileName: String?, val nodeName: String)`), splitting on first `/`. Test against all 18 real entries in `hcp_orig_en.hyp`, including both anomalies producing `fileName = null`.
2. `RefFile` model + parser: `RefEntry` sealed (`FileName`/`NodeName`/`AliasName`/`LabelName(name, lineNumber)`/`DatabaseName`), `RefModule(entries)` with a `files(): List<RefFileCatalog>` grouping helper (groups by "belongs to the preceding `FileName`"), `RefFile(modules)` with `find(fileName, nodeName): RefFileCatalog?` (case-insensitive, `.HYP`-suffix-tolerant, matching the corpus's own inconsistency). `RefFile.parse(bytes): RefParseOutcome`, sealed `Success`/`Failure(RefParseFailure)` mirroring `OpenOutcome`'s existing shape; bounds-check module length before allocating (same hostile-input discipline as `HypDocument.open`). Red: hand-built byte arrays (one-module/one-file/two-node case, multi-module case, a label with a line number, terminator-only empty file). Green: the parser.
3. Property-based round-trip test: generate 1–5 modules of random file/node/alias/label/database entries, encode exactly per spec + terminator, parse, assert structural equality. ~200 fixed seeds.
4. Record the task-0 finding in `doc/format-notes.md`; write `doc/progress/phase-12-ref-support.md`.

**Explicitly out of scope:** no filesystem resolver opening referenced `.hyp` files; no write/round-trip.

**Verification:** `./gradlew jvmTest wasmJsTest wasmWasiTest` green.

## Phase 13 — Traversal API: `resolve()`

**Model/effort:** Opus (low-medium — the "is this actually needed" judgment call, already made above) for the design; Sonnet (low) for the fill-in.

**Files:** `src/commonMain/kotlin/de/rholambdapi/hypp/ResolvedTarget.kt` (new).

```kotlin
sealed interface ResolvedTarget {
    data class ToNode(val node: Node) : ResolvedTarget
    data class ToImage(val image: ImageNode) : ResolvedTarget
    data class ToExternalRef(val ref: IndexEntry.ExternalRef) : ResolvedTarget
    data class ToSystemAction(val entry: IndexEntry) : ResolvedTarget   // SYSTEM/REXX_*/QUIT/CLOSE
    data object Missing : ResolvedTarget                                // index out of range
}
fun HypDocument.resolve(target: NodeIndex): ResolvedTarget
```

Existing API (`nodes`, `entries`, `tableOfContents()`, `node()`/`entry()`/`image()`) is otherwise sufficient — no other new code proposed for hierarchy/content iteration.

Red: table-driven test, one entry per `IndexEntry.TYPE_*`, asserting the right variant, plus an out-of-range index. Green: dispatch on `entry(target)?.type`.

**Verification:** `./gradlew jvmTest wasmJsTest wasmWasiTest`.

## Phase 16 — CLI commands + Round A (JVM fat jar)

**Model/effort:** Sonnet throughout (wiring against an already-designed model/renderer layer); Haiku for `ArgParser.kt` (mechanical given the fixed 4-command/≤2-flag surface from `doc/cli-design-space.md`).

**Files:** `hypp-cli/src/commonMain/kotlin/de/rholambdapi/hypp/cli/{ArgParser.kt, Commands.kt}`, `hypp-cli/src/jvmMain/.../Main.kt`.

- `dump <file> [--format html|markdown|asciidoc|org|ansi|epub]` (default `html`) — resolves against the registries; stdout for `Renderer`s, `--out <file.epub>` + `Zip.kt` for `epub`.
- `validate <file> [--strict]` — prints `document.diagnostics`; exit code per the hard/informational split (decision 15).
- `inspect <file>` — header, extended headers, TOC, entry counts by type, image count; uses `resolve()` (Phase 13) for links/cross-refs, including unresolved `ExternalRef`s (no `.REF` loading — just demonstrates the model).
- `extract-images <file> [--out dir]` — `ImageEncoder` per image (default `StoredPngEncoder`; JVM `Main.kt` wires `ImageIoPngEncoder` instead), `<name>.png` under `--out`.

**Round A "done":** `./gradlew hypp-cli:fatJar` produces a runnable jar; `java -jar hypp-cli/build/libs/hypp-cli-all.jar dump <corpus-file> --format html` produces output.

**Verification:** one test per command against `Commands.kt` directly, plus one `ProcessBuilder` smoke test running the built fat jar end to end (mirrors `wasmJsFacadeSmokeTest`'s external-process check).
